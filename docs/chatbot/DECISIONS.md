# Design Decisions

| # | Decision | Why |
|---|---|---|
| D1 | Build standalone with adapter interfaces (`PlatformDataAdapter`, `AuthProvider`) | No Grovator codebase available; keeps platform-specific guesses isolated |
| D2 | Mock data and a synthetic knowledge corpus for dev/tests, labelled as synthetic | Avoids inventing real platform behaviour while allowing tests |
| D3 | Model names come from env (`ROUTER_MODEL`, `ANSWER_MODEL`, `GUARD_MODEL`) | Groq deprecates models |
| D4 | Qdrant embedded (`:memory:`) for tests, docker Qdrant for dev (`QDRANT_URL`) | Fast hermetic tests; per-user choice from brief |
| D5 | RBAC is a Qdrant payload filter (`role_visibility`, `org_id`, `school_id`; `*` = platform-wide), built only from the JWT Principal. BM25 candidates come from the same scoped set | Retrieval can never return chunks outside the caller's scope, for both vector and keyword paths |
| D6 | Hybrid = vector top-12 + BM25 top-12 fused by RRF (k=60); confidence gate uses the best **cosine** score, not the RRF score | RRF scores are rank-based and can't express "nothing relevant" |
| D7 | `MIN_RETRIEVAL_SCORE=0.55`. Measured on the synthetic corpus: relevant min 0.699, off-topic max 0.478 | Threshold sits in the gap; **must be re-calibrated on real docs** |
| D8 | Student role exists and is the primary user: sample corpus focuses on kits (IoT, Robotics Foundation) and block coding | User answer, Phase 0 |
| D9 | English-only, so `bge-small-en-v1.5` is acceptable | User answer, Phase 0 |
| D10 | Chunk = 350 target / 400 max tokens, 40 overlap, sentence-packed, heading prefix in text, 1-line summary stored | Brief; summary used as fallback when the budget is tight (`compress.py`) |
| D11 | Token counting uses tiktoken `cl100k_base` as an estimate; Groq's `usage` is the source of truth in logs | Brief says tiktoken-compatible estimate |
| D12 | Models (checked against live Groq list, 2026-11-21): answer `openai/gpt-oss-120b`, router/summary/extractor `openai/gpt-oss-20b`, guard `openai/gpt-oss-safeguard-20b`. Llama chat models (3.1-8b, 3.3-70b) are no longer listed, so the "Llama only" rule was dropped with user approval | Only chat-capable models available; all env-swappable |
| D13 | `reasoning_effort="low"` sent only to gpt-oss models. Measured on the router call: 95 -> 42 output tokens | Hidden reasoning counts as output tokens and latency |
| D14 | Optional Phase 4 input screen: `meta-llama/llama-prompt-guard-2-86m` (still Llama, still available) | Cheap injection classifier before any chat model |
| D15 | One event generator (`ChatService.events`) feeds both `/chat` and `/chat/stream` (SSE: `meta`, `token`*, `done` / `error`) | No divergence between streaming and non-streaming behaviour |
| D16 | Router = one 20B call returning `{intent, query, reply}`; smalltalk is answered by the router itself (no retrieval, no big model). Unsafe / off_topic / my_data return fixed templates | Fewest calls per path. `my_data` stays a stub until Phase 4 tools |
| D17 | Session key `grovator:sess:{user_id}:{session_id}`; refusals/smalltalk write no memory; the turn is saved synchronously and the summary updated in the background (re-read before write) | A guessed session_id can't cross users; injected junk doesn't persist. Race window if the user sends a follow-up before the summary lands (they then still get the 2 raw turns) |
| D18 | Answer prompt budget enforced in `prompting.py`: drop oldest turn, then summary, shrink context; total input <= 1200 | Brief's hard budget |
| D19 | Router failure fails open to retrieval using `previous_user_msg + message` as the query; the confidence gate still blocks unrelated questions | Found live: raw follow-up under a rate-limited router lost context and missed the right doc |
| D20 | ANSWER_SYSTEM says "under 120 words"; `finish_reason == "length"` is surfaced as `truncated` | Live run: 1 of 12 answers hit the 350 cap and was cut off. After the fix 0 of 36 |
| D21 | Long-term memory lives in its own Qdrant collection `user_memory` (same vector DB + embedder as knowledge). Every read/write/delete is filtered by `(user_id, org_id)` from the JWT; memory ops never accept a user_id from a body, URL or the LLM | Brief: memory through the RAG pipeline, hard user filter |
| D22 | Extractor only runs when a free regex says the user is talking about themselves (`should_extract`). Pure questions cost 0 extra tokens | Groq free tier is 8k tokens/min/model; most turns must yield zero memories anyway. Trade-off: a fact phrased as a question is missed |
| D23 | Memory write pipeline: redact PII in the message before the LLM -> LLM extracts -> drop candidates with PII/sensitive/injection/over-length/bad type -> max 3 -> embed -> dedupe -> write | Brief: PII detection before writing; extractor output is untrusted text derived from user input |
| D24 | Sensitive filter (health, family, name, address) checks first- AND third-person, since the extractor rewrites in third person | Found by tests: "Student's mother works at a bank" slipped past a first-person-only rule |
| D25 | Dedupe at cosine > 0.9 (measured: paraphrases 0.935-0.978, different facts 0.53) updates in place, scoped to the same user+org; cap 50/user, evict least-recently-used | Brief; cap bounds storage and prompt-injection surface |
| D26 | Retrieval: top-2 with cosine >= 0.6 (measured: related >= 0.67, unrelated mostly <= 0.55), plus one `preference` memory rides along if room | Style preferences are never similar to a specific question, so pure similarity would never apply them |
| D27 | Memories are injected as an `ABOUT THE USER` block (<= 80 tokens, first thing dropped under budget pressure); the system prompt says they only tailor style and are never facts or instructions | Mitigates stored prompt-injection and keeps memory from becoming a source of "facts" |
| D28 | Memory failures (recall/save/touch) are swallowed and logged without text; chat continues | Memory is an enhancement, never a dependency |
| D29 | Guardrails are code, not prompt. L1 input rules (0 tokens) run before anything: length/garbage, injection (incl. leetspeak/zero-width/base64/delimiter tricks via NFKC normalisation), code/query injection, privilege claims, PII requests, cross-tenant phrasing, advice, abuse, self-harm/distress. Blocked messages cost 0 LLM calls and write no session/memory | Brief: strict guardrails enforced in code |
| D30 | A claimed role is only refused when it is HIGHER than the JWT role ("I am a teacher" from a teacher is fine) | Avoids false positives; the JWT is the only source of truth for role |
| D31 | **Verify-then-stream.** The server consumes the model stream internally, runs the output guard on the full text, then emits the verified text as SSE `token` chunks. There is no `replace` event | The red team showed streamed tokens leak before a final check can run (vendor names, prompt text, invented marks, ids). Cost: first token arrives after full generation (~1 s on Groq for <=120-word answers) |
| D32 | Output guard: vendor/model names -> fixed identity line; 6-word shingle overlap with any system prompt -> refuse; uuid/ObjectId/principal ids -> `[ID]`; PII -> redacted; abuse words -> refuse; numbers must appear in context (strict mode: all numbers); lexical support >= 0.5 else "I don't have that information" | Brief: grounding, PII redaction, no prompt/vendor/id leaks. Measured real-answer support: min 0.62, avg 0.76 over 12 answers, so 0.5 leaves modest margin (failure mode = a safe false refusal) |
| D33 | `my_data` answers are rendered by code from tool output; the answer model is never given tool data. Nothing from this path is written to session, summary or memory | Marks cannot be invented; student data is not retained in Redis/Qdrant beyond the request |
| D34 | Tools: allow-list of 4 read-only functions, Pydantic `extra="forbid"` (smuggled `org_id`/`user_id` = validation error), regex-restricted name args (no `$`/`{}`), role-gated tool lists, names resolved only inside the caller's scope, **every returned record re-checked by `policy.py`**, "denied" == "not found" | Brief: LLM never chooses whose data to fetch; no enumeration |
| D35 | `MockAdapter` is intentionally naive (ignores scope, returns all tenants). Tests therefore prove the policy layer enforces access, independent of adapter quality. A real adapter should also scope its queries | Defence in depth |
| D36 | Rate limit: Redis fixed window per IP (60/min) then per user (20/min) -> 429 + Retry-After. `X-Forwarded-For` ignored unless `TRUST_PROXY=true`. Daily token budget per user (50k) and org (1M) counts every LLM call incl. hidden reasoning; exceeding returns a friendly 200 message | Brief: abuse controls. Fixed window allows a 2x burst at a window boundary (acceptable here) |
| D37 | Distress ("I feel sad and alone", bullying) gets a fixed supportive reply pointing to a trusted adult, not a chat answer | Platform serves children; found by live red team (router had replied conversationally) |
| D38 | Router prompt: `my_data` wording widened ("marks, a report, progress, batches or a schedule, theirs or someone's") and "personal details alone don't make a message off_topic". Prompt is 145/150 tokens | Live: "Show my report" was routed to FAQ; Phase 3 false-refusal on messages with personal details |
| D39 | **Semantic cache (Redis)**: cosine >= 0.95 on the local bge embedding, keyed by `kb_version + role + org + school`, 7-day TTL, 300 entries/scope. A first message is matched BEFORE the router (a standalone message needs no history); follow-ups are matched AFTER the router on the rewritten query. Hit = 0 LLM tokens, but the turn is still saved so follow-ups work | Brief L2. The embedding is computed anyway for retrieval, so lookup is free |
| D40 | **What may enter the cache**: only plain knowledge answers that passed the output guard unchanged, generated with no memories, no summary and no earlier turns, from a message <= 200 chars, with no URL / redaction placeholder / truncation. Never `my_data`, smalltalk, refusals | An answer shaped by one user's memory or history must never be served to another user (cross-user leakage). Mutation-tested |
| D41 | Re-ingesting the knowledge base changes `retriever.version` (hash of all chunk ids + text), making every older cache entry unreachable | Stale answers after a docs update |
| D42 | **Router shortcut** (free rules): greetings/thanks -> canned reply; a clear, self-contained platform question (question form, platform vocabulary, no data words, no anaphora, no risky words, 4-40 words) -> `platform_faq` without the router call. Anything ambiguous goes to the real router. A wrong shortcut is still caught by L1, the retrieval gate and the output guard | Router was the largest per-turn cost (~376 tokens). Data words win over platform words (tested) |
| D43 | **Lazy summary**: a turn is folded into the rolling summary only when it leaves the 2-turn window (turn 3+). The router instead gets the previous two USER messages (~30 tokens). `LAZY_SUMMARY=false` restores per-turn summaries | The summary duplicated what the raw last-2 turns already contain; a summary call cost ~240 tokens/turn |
| D44 | **Compression**: sentence-level selection with local embeddings. Keep sentences scoring >= 0.9 x the chunk's best (max 2 cores) plus 1 neighbour each side ("sentence window"); drop chunks whose best sentence < 0.6 (rank 1 always kept); then the hard token budget. Calibrated on 15 questions: 24% fewer context tokens, 15/15 key facts retained | A window of 0 saved 34% but lost a fact (the worked example next to the best sentence). Facts beat tokens. Corpus chunks are short, so real docs should compress more |
| D45 | Observability: one JSONL line per request (`ts, role, org, school, hashed user, intent, cache_hit, shortcut, input/output/router tokens, model, latency_ms, refused_reason, memories_used, truncated, tool`) built from a fixed whitelist (no field can hold text), plus Redis aggregates per (org, school, day) and per-component token counters. `GET /admin/chatbot/usage?days=&school_id=`: admin -> own school only; superadmin -> own org or one school | Brief: log fields + usage endpoint; privacy: never log message text |
| D46 | Output guard numeric rule narrowed: in FAQ answers only performance-type claims (`%`, score/mark/grade/rank/attendance/"out of"...) must appear in the source; strict mode (tool answers) still requires every number | The baseline benchmark showed a false refusal of a legitimate real answer under the old ">10 and not in source" rule |
| D47 | Grounding threshold lowered 0.5 -> 0.35 (lexical support). Calibration on real retrieval: good paraphrased answers scored 0.44-1.00, plausible hallucinations ("connect over Bluetooth with the Android app") 0.12-0.20. A semantic (embedding) check was tried and **rejected as an override**: plausible hallucinations score 0.73-0.75, the same as good paraphrases | Benchmark showed a real answer refused at 0.44. In the Phase 4 baseline it only passed because per-turn summary text padded the grounding source. Lexical grounding remains a heuristic |
| D48 | Follow-up caching (matching a REWRITTEN query mid-conversation) is **off by default** (`CACHE_FOLLOWUPS=false`). Only first messages are cached/matched | Benchmark: "I forgot it" was rewritten to a login question and served the generic login answer, ignoring what the user said. A cached answer cannot see the user's actual wording or context |
| D49 | Numeric rule (FAQ answers) narrowed again: bare `%` no longer triggers; only numbers near performance/progress words (score, marks, rank, attendance, progress, completed, average...) must be in the source. Strict mode (tool data) unchanged | Live run refused a robotics answer containing "50% speed" at support 0.69 |
| D50 | Widget = a self-contained Next.js component (`ChatWidget`) that takes only `apiUrl` + `getToken`. It never mints, inspects or stores the JWT. Browser calls FastAPI directly; no Next.js proxy, no keys in the frontend (build checked for `gsk_`/`GROQ_API_KEY`) | Brief: Groq key only on the backend |
| D51 | Model/user text is rendered through a tiny markdown subset into React elements only (no `innerHTML`, links or images) | Model output is untrusted; tested with `<img onerror>` / `javascript:` payloads |
| D52 | Feedback: `request_id` on every answer; one changeable rating per request; only the requesting user can rate it (others get 404); thumbs-down takes a fixed reason enum, **no free text** | Free-text feedback would be an uncontrolled PII channel for children |
| D53 | CORS allow-list from `CORS_ORIGINS`; `*` is ignored; no credentials (bearer tokens); `Retry-After` exposed | Browser calls the API directly |
| D54 | Per-user conversation persistence is opt-in (`storageKey` prop, sessionStorage, last 40 messages) | On a shared school computer one user's chat must never reappear for another |
| D55 | Eval harness is data-driven JSONL with two modes. Offline = deterministic gates (LLM stubbed); live = real Groq. Security suites gate at 100%, quality at 90% (configurable). Gates verified by mutation | Brief: eval script printing pass rate, avg tokens, p95 latency |
| D56 | Startup refuses to run with `ENVIRONMENT=production` and a default/short JWT secret, no Groq key, mock adapter, in-memory Redis/Qdrant, or localhost/`*` CORS. JWTs must carry `exp` and `sub` | A fake-data or default-secret deployment must be impossible to ship by accident |
| D57 | `Source:` line lists only documents the answer actually uses (word overlap: best source + any within 75% of it) | A kit question was showing an unrelated kit guide as a source |
| D58 | Numeric grounding checks numbers against ALL retrieved text, not just the compressed excerpt the model saw | Live eval: a correct variables answer refused because compression had dropped the sentence holding its numbers |
| D59 | **Demo-first UX.** The demo page renders the course content (courses, 8 lessons, 7 block-reference pages, sample block programs, platform tools) fetched from `GET /content`; the bot answers from the SAME documents (one source of truth, same visibility rule). Demo login is `POST /demo/session` (`DEMO_MODE=true`, refused in production) so there is no token box | User wanted a simple demo: chat about what is on the page, remember the conversation, answer only about the platform |
| D60 | **Page-aware RAG**: the widget sends the open page's `source`; the server ignores it unless the user may see it (hidden == unknown). Questions that point at the page ("this", "these", "step 3") rewrite the query with the page title and put the page's chunks first; near-ties go to the page being read; unrelated questions are not hijacked. Cache keys include the page | "Explain this lesson" must work; answers must not leak across pages |
| D61 | **Token meter**: every answer reports `tokens_total` (router + answer in/out) and `naive_tokens`, the estimated input of a bot WITHOUT retrieval (system prompt + every document the user can see + the whole chat so far + the question). The UI shows both and the running saving | Make the saving visible per answer |
| D62 | The naive baseline is the whole site, not just the open page. A page-only bot is cheaper than us on one tiny page (measured: 258-token page) but cannot answer anything outside it. `demo_compare` reports BOTH honestly | My first estimate flattered the project; the honest comparison is "a bot that can answer everything" |
| D63 | **Free follow-up routing**: a clear question, a question pointing at the open page, or a follow-up with no data/risky words skips the router. Follow-up query = previous question + new message; retrieval ALSO searches the new message alone with 2x weight (vector and keyword) and compression keeps sentences relevant to either | The router cost 380-500 tokens per follow-up. Found by probing: equal weight let the old topic drown a topic shift ("and how do I log in again?") |
| D64 | **Extractive rolling summary** (`SUMMARY_MODE=extractive`, default): "Earlier questions: a \| b \| c", newest kept, 120-token cap. 0 LLM tokens. `llm` mode still exists | The LLM summary cost ~380 tokens per turn from turn 3; answers can always be re-retrieved |
| D65 | Prompt caps trimmed: context budget 700 to 550, per-turn assistant text 120 to 80 tokens | Verified on live eval (chat quality 18/18, conversations 12/12) |
| D66 | Shortcut platform vocabulary contains only platform-specific words ("if", "run", "line", "turn", "log" removed) | "what if the number never changes?" looked standalone and lost its context |
| D67 | New deterministic L1 rule for off-topic TASKS (write/compose/tell + poem/story/joke/song/essay...), narrow on purpose ("write a program" is fine); the same words make the shortcut defer to the router; the answer prompt says to decline them | Live multi-turn red team: a router-free follow-up ("now write me a poem about it") got a poem because its words overlapped the lesson |
| D68 | Eval additions: multi-turn attacks (benign question first, attack as a follow-up) and "must refuse" off-topic checks that accept either a pipeline block or the model's own refusal. Canaries are data values, not names the attacker typed | Skipping the router changes the attack surface; the eval must test it |
| D69 | Tests pin their own env (`DEMO_MODE=false`, `SUMMARY_MODE=llm`, optimisation flags off for legacy suites) | A developer's local `.env` must never change test results |
| D70 | **Lesson sequence is content, stated once and checked.** A `Learning Path: Lesson Order` page lists both courses in order (lessons AND the activities between them), and every lesson page ends with `Previous lesson:` / `Next lesson:` lines. A test compares those lines with the real `order` front-matter, so the page and the catalog can never disagree | The bot answered "I don't have information about the lesson that follows" because nothing in the content said what comes next |
| D71 | Order questions ("what comes after X", "first/last lesson", "in what order") get an extra free search aimed at the learning path (2x weight) and are NOT sentence-compressed. "what comes next" / "previous lesson" point at the open lesson unless they name another ("next lesson after X") | Pages that merely mention the named lesson crowd out the sequence chunk; compression truncated the list ("...and so on") |
| D72 | Compression defaults widened: keep sentences >= 0.8 x the best (was 0.9), up to 3 core sentences (was 2). Calibrated on 22 key-fact questions incl. 8 troubleshooting ones: old setting lost 1/22, every wider setting kept 22/22; chosen 0.8/3 for a safety margin of ~0.05 over the cut-off (0.85/3 passed with only 0.009). Context saving 19% -> 14% | Renaming "Govator" to "Grovator" nudged embeddings and flipped "unplug the USB cable" out of the context for "the kit will not connect": the margin was razor-thin. Troubleshooting answers are "If it does not..." sentences that rank below the generic setup sentence |
| D73 | The platform is **Grovator**. "Govator" (a common misspelling) in a user message is corrected to "Grovator" at the input guard, so retrieval and the model see the real name | The product name was misspelled throughout the first versions; users make the same mistake |
| D74 | **Real gateway dataset replaces the dummy corpus.** The JSON is the source of truth; `rag/hardware.py` renders documents from its records at load time (device guide, interface, wiring rules, concepts), used by BOTH ingestion and the page catalog. Old dummy docs moved to `tests/fixtures/knowledge_synthetic/` so the 549 mechanics tests stay meaningful | Nothing per-sensor is hardcoded: a test adds a device to the JSON in memory and it appears in docs, aliases and the interface page |
| D75 | Relationships are rendered into the text: a device guide carries its interface's pins/connector and only the wiring rules that apply to it; an interface page lists the devices using it | Retrieval returns the wiring and the gateway pins together |
| D76 | Wiring steps are generated from each device's own fields; every guide has explicit "components", "wrong pins", "after wiring" and "troubleshooting" sections that state what the dataset does NOT cover (code, readings, fault outcomes, cables) | The dataset has none of those facts; the model gets the gap in front of it instead of filling it (live run: it invented jumper wires and short-circuit outcomes before these sections existed) |
| D77 | **Sensor focus**: names/aliases derived from the JSON are detected in each message and stored in the session; follow-ups that continue the conversation get the sensor name added to the search (replaces the free "previous question" glue), general/list questions do not. Ambiguity (no sensor named and none in focus, or two in focus plus "it") returns a free clarifying question | "What should I do after connecting it?" must find THIS sensor's page; "Which sensors can I connect?" must not be forced back to it |
| D78 | **Invented-pin guard**: GPIO numbers in an answer must appear in the retrieved records (a pin the student named may be mentioned only in a negating sentence); otherwise a fixed safe reply | A made-up pin is the worst hardware answer and lexical grounding cannot see it |
| D79 | Answer prompt rewritten for the gateway (still 200 tokens). `pin is ...` is a credential only when 3-8 digits follow | Live run: "no GPIO pin is used twice" was redacted to "[CREDENTIAL]" |
| D80 | Eval has `--corpus gateway` (default, real data, new FAQ/conversation sets) and `--corpus synthetic`; security sets are shared. Compression/grounding thresholds were calibrated on the synthetic corpus and are NOT re-calibrated for the gateway | Honest limitation, see BUGS.md Phase 9 |
| D81 | **Direct device lookup**: when the sensor is known (named, in focus, or the open device page with "this"), retrieval reads only that device's guide, 2 sections, chosen by what the question asks (troubleshooting / after wiring / components / safety / wiring). No whole-knowledge-base search | User report: "for alcohol sensor" searched everything and pulled in the open Flame Sensor page |
| D82 | Direct lookups send **no chat history**: the question is rewritten to carry the device name ("What if it is not working? (Ultrasonic Sensor)") and the context is that device's guide, so history adds tokens, not information | Live: -60 to -180 input tokens per follow-up; live eval quality unchanged (see BUGS Phase 10) |
| D83 | Generated guides tightened: headings no longer repeat the device name (every chunk is prefixed with the title), the record + steps + gateway pins are one "How to wire" section, the "not documented" sections are half as long. Every JSON field is still present verbatim (test) | Ultrasonic guide ~820 -> 585 tokens |
| D84 | Answer prompt 200 -> 162 tokens, every rule kept; adds "answer exactly what was asked, no headings, no repeating the question" to cut output tokens | Output tokens were the second-largest cost |
| D85 | **Reuse of direct answers across students**: scoped by knowledge version + role/org/school + device + sections; only questions with no specifics (no digits, no "I am"/"my name"); cosine >= 0.95 AND the same pin/negation words (VCC vs GND, "not working" vs "working"). History-free answers are what make this safe | A class asking "what if it's not working?" about the same sensor pays once |
| D86 | **Provider switch**: `LLM_PROVIDER=gemini` uses a Gemini REST client (httpx, no SDK) with the same interface; default model `gemini-3.5-flash-lite` for answer and router (env-driven; chosen from the models the key can list). Answers are consumed whole server-side, so no streaming API is needed. Key in a header, never in URLs, logs or error text. Groq remains the default and keeps working | Requested; flash-lite is the cheap model class. Live eval (100 turns): chat 29/29, conversations 16/17, controls 7/8 (two stale expectations, fixed), red team 46/46, security 150/150; 354 tokens/turn vs 546-608 on Groq gpt-oss; pin guard triggered 0 times. Single run, not repeated |
| D87 | **Pre-written answers** (`chat/canned.py`, `ENABLE_CANNED`): plain "what is X / how do I connect X / which pins does X use" questions about ONE named device (or the one in focus), plus a few gateway facts (what is the gateway, which sensors, which pins are digital/analog/I2C/UART, the wiring rules) are answered by templates rendered from the JSON: 0 tokens, no model, no search, same answer every time. Matching is rule-based and strict: any digit/GPIO of the student's own, "and/or/vs/if/why/after/not/wrong...", two devices, or a second question sends it to the model. "What is X" is templated only if the dataset defines X (concepts); otherwise the model explains it (D84) | User asked for pre-defined answers for basic questions. On the 29 FAQ test questions 14 match (the set is biased toward these shapes; real share unknown until measured on real traffic) |

| D88 | **File-based knowledge base** (`backend/knowledge/`: applications, sensors, blocks, kits, media as YAML, pydantic models with `extra=forbid`, `python -m knowledge.validate`, `python -m ingest.run`). Sections are indexed whole: code listings, pinouts and tables are never split. The loader cross-checks references and that every code listing parses as Python | The user must be able to add applications/sensors/blocks/kits by dropping files |
| D89 | **Deterministic structured answers** (`chat/appkb.py`): wiring table, block stack, code, line-by-line, thresholds, steps, FAQ and "not documented" are built from the files in code (0 tokens). The frontend renders them (table, block stack, code card with copy, images) | "Never guess a pin": a table built from YAML cannot contain a pin the YAML does not have; also the cheapest path |
| D90 | **Two kits, no invented mapping**: the lesson's ESP32 kit is documented; the Grovator controller (from photos, `verified: false`) is not wired to the pulse oximeter anywhere. Any question connecting them gets "I don't have that detail yet". `GAPS.md` lists it | The controller's GPIO numbers differ from the ESP32's (GPIO22 is Relay 2 vs I2C SCL) |
| D91 | **Two sensors, one conflict surfaced**: `Pulseoximeter_V2.0.pdf` (UART, RX/TX, 9600 baud) is a separate sensor from the I2C MAX30102 of the lesson; the widget pin list (3V3/GND/RX/TX) in the MAX30102 PDF is treated as a copy of the V2.0 one, not as a pin list for the lesson | Resolves most of the I2C-vs-UART contradiction without picking silently; flagged in GAPS.md for confirmation |
| D92 | **General mode** (`Intent.general_tech`, `GENERAL_SYSTEM`): "what is SpO2 / I2C / a relay" are answered from model knowledge in simple words: no retrieval, no "sources", no grounding check, but leak checks stay and a GPIO number not in the knowledge base blocks the answer. Detected by rules first (definition cue + technology word + no device named), router second | The brief wants flexible answers for general questions and strict ones for hardware facts |
| D93 | **Health note**: whenever the question touches readings/health (SpO2, BPM, oxygen, accurate, diagnose...), a fixed sentence "learning project, not a medical device..." is appended in code, on every path (deterministic, general, grounded) | Cannot depend on the model remembering |
| D94 | Prompts moved to `backend/config/system_prompt.yaml`; answer prompt stays <= 200 tokens (asserted). Brand is "Grovator" in replies (the input guard normalises "Govator") | Brief asked for a config file |
| D95 | **Long-term memory off by default** (`ENABLE_LONG_TERM_MEMORY=false`); the memory suites pin it on. Students are anonymous, and the extraction call was a hidden model call after deterministic answers | Brief: no personal identifiers; token control |
| D96 | The gateway dataset's own `pulse_oximeter` entry (generic "Verify module voltage") is **superseded** by `sensors/pulseoximeter_max30102.yaml` (`supersedes:`); other gateway devices are unchanged | Two sources for the same sensor would have conflicted |
| D97 | Feedback also appended to `logs/feedback-<day>.jsonl` (random request id, intent, rating, fixed reason; no user/org). Images served from `/media` (StaticFiles) | Brief: thumbs logged to JSONL without personal identifiers |
